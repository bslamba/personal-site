## Cheat sheet

| | |
|---|---|
| **Recommended method** | **GUI**, from Cisco ISE 3.2 patch 3 onwards |
| **Node order** | **SAN first** → PSNs (in batches) → MnT → **PAN last** |
| **Why SAN first** | The PAN stays on the old version and can be used for rollback if the upgrade fails |
| **Pre-upgrade, mandatory** | Back up all configuration and monitoring data · Export the internal CA key and certificate chain · Back up server certificates for all nodes |
| **Full upgrade** | All nodes simultaneously. Faster. **Services unavailable during it.** |
| **Split upgrade** | Batched. Services stay available. Takes longer. |
| **PSN upgrade time** | Roughly **90–120 minutes each** |
| **Auto rollback** | PAN and MnT roll back automatically on failure. **PSNs do not** — manual intervention required. |
| **CLI commands** | `application upgrade prepare <bundle> <repo>` then `application upgrade proceed` |
| **Support bundle** | Automatically generated by GUI and CLI upgrades, saved to the repository if writable |
| **GUI method limitation** | **Not supported on OCI, AWS or Azure** |

---

An ISE upgrade touches the system that authenticates every device on your network. This is the full sequence — what to do before, how to choose a method, how each one executes, and what happens when something fails.

Written against the Cisco ISE 3.5 upgrade documentation, and applicable in structure to the 3.x line generally.

## Part 1 — Prerequisites

### The three mandatory backups

Cisco's pre-upgrade task list is short and non-negotiable:

<ol class="steps">
<li><strong>Back up all configuration and monitoring data.</strong> Both. The configuration backup holds your policy; the operational backup holds your logs and reports.</li>
<li><strong>Export the internal CA key and certificate chain.</strong> This is the one people forget, and it matters enormously if you use the internal CA for BYOD. Without it, every certificate you've issued becomes unverifiable after a rebuild.</li>
<li><strong>Back up server certificates for all Cisco ISE nodes.</strong> Every node, not just the PAN.</li>
</ol>

<div class="callout">
<p><strong>A backup you have not restored is a hypothesis.</strong> Restore the configuration backup onto a spare node or lab instance and confirm it works. This is the single highest-value hour in the whole exercise, and it is routinely skipped.</p>
</div>

### Everything else worth checking first

**Certificates across every node.** System certificates, the EAP authentication certificate, portal certificates, admin certificates, and the CA chain in the trust store. An upgrade window is the worst possible time to discover an expiry, because now you have two problems and no way to tell which caused the symptom.

**Repository reachability.** Configure the repository and test it with an actual file transfer before the window. Repository failures are a common cause of an upgrade that stalls at step one. This also matters afterwards: **the upgrade automatically generates a support bundle, and if the repository is reachable and writable it saves there** — otherwise to local disk.

**RADIUS server groups on your network devices.** Every switch and WLC should have more than one PSN configured. If a switch knows about exactly one PSN, upgrading that PSN is an outage for everything behind it. Fixing this is a network change, not an ISE change, so discover it early.

**Disk space**, particularly on MnT nodes.

**Licence entitlement** for the target version, and the UDI recorded for every node — Product ID, Version ID, Serial Number.

**A baseline.** Capture `show version` and `show application status ise` on every node, current authentication rate, active session count, and a screenshot of healthy Live Logs. "It seems slower afterwards" is unactionable; a before-and-after number is a diagnosis.

**Read the deprecations in the release notes.** Feature removals cause more upgrade problems than feature additions.

**Starting with Cisco ISE release 3.2 patch 3, upgrading through the GUI is the recommended method.**

Two important constraints:

**The GUI method is not supported on cloud platforms** — Oracle Cloud Infrastructure, Amazon Web Services, or Azure. Cloud deployments use the CLI.

**Backup and restore is limited to Cisco ISE release 3.2 patch 2** as a supported upgrade path in the current documentation.

### Why the GUI method is recommended

- During the upgrade, the **secondary PAN is moved into an upgraded deployment automatically and upgraded first**
- On failure, you can choose to **continue or cease** the upgrade — resulting in a dual-version deployment
- It requires **limited technical expertise**, so a single administrator can run it
- The upgrade is automated with minimal intervention
- You can **choose the upgrade order of PSNs** to maintain continuity where redundancy exists

## Part 3 — The node sequence

This is the part that must be right.

**Upgrade the nodes in this order:**

<ol class="steps">
<li><strong>Secondary Administration Node (SAN).</strong> At this point the PAN remains at the previous version and can be used for rollback if the upgrade fails.</li>
<li><strong>Policy Service Nodes.</strong> In distributed deployments, upgrade the nodes at the site with the SAN. You can select a group of PSNs to upgrade together, then <strong>verify success and run network tests before proceeding with the next set</strong>.</li>
<li><strong>Monitoring nodes.</strong></li>
<li><strong>Primary Administration Node, last.</strong> After upgrading the PAN, rerun upgrade verification and network tests.</li>
</ol>

**After the upgrade, the SAN becomes the PAN and the original PAN becomes the SAN.** If you want the original arrangement back, use **Promote to Primary** in the Edit Node window.

**If the upgrade fails during PAN registration**, the system initiates a rollback and changes the node to standalone mode. Upgrade it as a standalone via the CLI, then register it to the new deployment as a SAN.

### "No SAN in the Deployment"

A common error, with three causes and three fixes:

| Cause | Fix |
|---|---|
| No SAN configured in the deployment | Configure a SAN and retry |
| The SAN is down | Bring the node up and retry |
| The SAN has been upgraded and moved to the upgraded deployment | Use the CLI to manually upgrade the remaining nodes |

## Part 4 — Full upgrade versus split upgrade

The GUI offers two options at **Administration → System → Upgrade → Upgrade Selection**.

### Full upgrade

- Upgrades **all Cisco ISE nodes simultaneously**
- Completes **faster** than split upgrade
- **Makes application services unavailable**, because all nodes are upgraded in parallel
- Supported for all latest ISE releases

Choose this when you have a genuine maintenance window and can accept an authentication outage for its duration.

### Split upgrade

- Upgrades the deployment **while other services remain available**
- Updates the network or load balancers to keep nodes available for authentication
- **Limits downtime by dividing nodes into batches** and upgrading each in sequence
- **Takes longer** than a full upgrade
- Available for upgrading from ISE 3.2 patch 3 and later to 3.3 and later

**The new split upgrade framework**, introduced in 3.2 patch 3, brought three improvements:

- **Prechecks are completed before the proceeding phase**
- **The data upgrade occurs during the precheck phase**, reducing total upgrade time and preventing the system becoming unavailable
- You can **select PSNs and MnT nodes during the first iteration with the secondary PAN, or during the last iteration with the primary PAN**. Selecting them in the same iteration upgrades them simultaneously, reducing time further.

**Choose split when you cannot take an authentication outage.** Choose full when you can, because it's simpler and quicker.

## Part 5 — Executing a GUI upgrade

### Starting

<ol class="steps">
<li>Navigate to <strong>Administration → System → Upgrade &amp; Rollback</strong></li>
<li>In the Upgrade Selection window, click <strong>Full Upgrade</strong> (or Split Upgrade)</li>
<li>Click <strong>Initialize</strong></li>
<li>Click <strong>Next</strong> in the Welcome window to start the workflow</li>
<li>Complete every task in the <strong>Checklist</strong> window — this exists to avoid blockers and downtime</li>
<li>Optionally click <strong>Print Checklist</strong> to download it</li>
<li>Tick <strong>I have reviewed the checklist</strong> and click <strong>Next</strong></li>
</ol>

### Prechecks

In the Prepare to Upgrade window:

- Choose the **Repository** holding your upgrade bundle
- Choose the **Bundle**
- Choose the **Patch** for the release you're upgrading to

Prechecks then run against every node.

### Staging and upgrade

<ol class="steps">
<li>After prechecks complete for all nodes, click <strong>Start Staging</strong>. During staging the system copies the upgraded database file to all nodes and backs up configuration.</li>
<li>Click <strong>Next</strong> to reach the Upgrade Nodes window, showing overall progress and per-node status.</li>
<li>Click <strong>Start</strong>. Just before completion the system displays <em>"The system is about to upgrade. Logging out."</em></li>
<li>Click <strong>OK</strong>. <strong>Log in to the secondary PAN to monitor progress</strong> — use the secondary PAN dashboard to watch the primary PAN upgrade, then the primary PAN afterwards.</li>
<li>Click <strong>Next</strong> to check whether all nodes upgraded successfully. Failed nodes are listed in a dialog; clicking OK deregisters them from the deployment.</li>
</ol>

**Download the diagnostic reports from the Summary window** — checklist, prepare-to-upgrade, upgrade report, and system health checklist items. Don't click **Exit Wizard** until you've done this, or you lose easy access to them.

### Timing and batching

**Each PSN takes around 90–120 minutes to upgrade.** Upgrading a large number sequentially takes considerable time.

Cisco's best practices:

- **If you have a large number of PSNs, group them into batches** and upgrade each batch separately
- **Begin the upgrade only when nodes are in the active state**
- Monitor progress from the Admin portal

That 90–120 minute figure is the number to build your window around. Twelve PSNs done sequentially is potentially 24 hours; in batches of four with verification between, it's a different plan entirely.

## Part 6 — CLI upgrade

For cloud deployments, or when you want node-by-node control.

Two commands, **in this order**:

```
application upgrade prepare <upgrade bundle name> <repository name>
```

```
application upgrade proceed
```

**What `prepare` does:** copies the upgrade bundle from the remote repository to the local disk of the ISE node and extracts it. **Saving the bundle to local disk first reduces the time required for the upgrade** — you don't want a large download happening inside your window.

On a standalone node running Administration, Policy Service, pxGrid and Monitoring personas, you can also run the combined form:

```
application upgrade <upgrade bundle name> <repository name>
```

Copy the bundle to local disk before running it.

The CLI path supports standalone nodes, two-node deployments and distributed deployments, following the same node ordering described above.

## Part 7 — Rollback

Be honest about what rollback means before you need it.

**GUI and CLI upgrades:**

- **If an upgrade fails on a PAN or MnT node, the nodes are automatically rolled back.**
- **If a PSN fails to upgrade, it does not roll back automatically** — manual intervention is required.

**On failure you can choose to continue or cease**, which results in a **dual-version deployment**. That's a legitimate intermediate state, not a broken one, but it's a state you should decide about deliberately rather than by default.

**Manual rollback** means:

<ol class="steps">
<li><strong>Deregister the node</strong> to remove it from the deployment</li>
<li><strong>Reimage the node</strong> — remove from deployment, install ISE, then apply the latest patch to the newly installed release</li>
<li>Restore from backup and re-register</li>
</ol>

**For backup-and-restore upgrades, rollback follows the same procedure as reimaging.** When you reimage nodes, all information and configuration from the previous deployment is erased.

<div class="callout">
<p><strong>Decide your abort point before the window opens.</strong> "If we are not through the PSNs by 03:00, we stop." Written down, agreed in advance, and enforced by someone who isn't the person doing the work.</p>
<p>Reimaging and restoring is measured in hours per node. If your window is four hours and rollback takes six, you do not have a rollback plan — you have a hope.</p>
</div>

## Part 8 — Verification and post-upgrade

### Immediately, per node

```
show application status ise
show version
```

Every service running, correct version.

```
show logging system ade/ADE.log tail
```

Application start and stop events appear here. A service that failed to start says so.

**After each batch of PSNs, verify upgrade success and run network tests before proceeding.** This is Cisco's explicit guidance and it's the mechanism that stops a bad upgrade propagating across the whole estate.

### Test the full matrix

Each of these paths can break independently:

- Wired 802.1X
- Wireless 802.1X
- MAB
- Guest access and portal
- BYOD onboarding
- Posture assessment
- TACACS+ device administration
- **CoA specifically** — it's the dependency everything advanced relies on, and it fails silently

### Then

- Compare against the **baseline** you captured beforehand
- Confirm **all debug logging is off**. In 3.5 the new time-restricted debug feature reverts automatically after a timer; in earlier versions, check manually — and remember that "Reset to Default" while a Debug Profile is enabled leaves the template active while the components revert
- Verify **node sync state** on the Deployment page. A PSN that is out of sync still authenticates, using stale policy
- Take a **fresh backup** on the new version
- **Leave the change record open for a week.** Some problems only surface with a full business cycle — the monthly batch job, the contractor who visits on Thursdays, the certificate that renews at month end

### If it went wrong

**The upgrade automatically generates a support bundle specific to the upgrade.** If the repository is reachable and writable, it saves there; otherwise to local disk. That bundle is what TAC will ask for, and it's already been created for you.

## The short version

Back up everything including the internal CA key. Verify the backup by restoring it. Confirm your network devices have redundant PSNs. Use the GUI method if you're on 3.2 patch 3 or later and not in cloud. Upgrade the SAN first and the PAN last. Batch your PSNs and verify between batches. Budget 90–120 minutes per PSN. Know that PSNs don't auto-rollback. Decide your abort point in advance.

Almost every ISE upgrade that goes badly failed at one of those points, and every one of them is decided before the window opens.
